# Правила класифікації PARA (довідка для навички second-brain)

Завантажуй цей файл лише тоді, коли клас нотатки неочевидний (progressive disclosure).

## Послідовність запитань
1. Нотатка — це сирий запис, який ще не опрацьований? → **Inbox** (`status: inbox`).
2. Є конкретний результат **і** дедлайн або чітке завершення? → **Projects** (`type: project`).
3. Це довготривала відповідальність без кінцевої дати? → **Areas** (`type: area`).
4. Це довідковий матеріал на тему, яка може знадобитися? → **Resources** (`type: resource`).
5. Нотатка неактуальна або завершена? → **Archives** (`status: archived`).

## Типові приклади
| Приклад | Клас | Чому |
|---------|------|------|
| Здати лабораторну роботу до пʼятниці | Projects | є результат і термін |
| Навчання на спеціальності | Areas | постійна сфера, без кінця |
| Конспект про Git | Resources | довідковий матеріал |
| Стара чернетка вимог | Archives | замінена новою версією |
| Рядок-ідея, записаний «на льоту» | Inbox | ще не опрацьовано |

## Спірні випадки
- Якщо нотатка підходить до двох класів, обирай **найбільш дієвий** (Projects > Areas > Resources > Archives) і зазнач альтернативу в журналі змін.
- `type: moc` — карта змісту; зазвичай лежить в Areas, бо описує сферу.
- Не переміщуй нотатку між класами без підтвердження користувача.
